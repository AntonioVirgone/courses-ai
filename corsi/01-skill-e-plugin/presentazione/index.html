01 Perché skill e plugin

Ogni sessione l'agente riparte da zero

Prompt ripetuti

«Usa i conventional commits, scope in minuscolo, issue in fondo…» lo riscriviamo a mano ogni volta, e ognuno a modo suo.

Conoscenza tribale

Il modo giusto di fare un ADR, una review, un rilascio sta nella testa di due persone. L'agente non lo sa, i nuovi arrivati nemmeno.

Contesto sprecato

Mettere tutto nel file di istruzioni globale (CLAUDE.md, copilot-instructions.md) gonfia ogni richiesta, anche quando quelle regole non servono.

Una skill è una procedura scritta una volta: una cartella con un SKILL.md che l'agente carica solo quando serve. Un plugin è il pacchetto che porta skill, agenti, hook e server MCP sulle macchine di tutto il team, con versioni e aggiornamenti.
Partire da un esempio concreto del team: quante volte avete spiegato all'agente come scrivere un commit o un ADR? Quello è il candidato perfetto per una skill.

01 Perché skill e plugin

Quando usare cosa

StrumentoChe cos'èUsalo per
Istruzioni di progettoCLAUDE.md, .github/copilot-instructions.md, AGENTS.mdRegole sempre valide e brevi: layout del repo, lingue, convenzioni.
SkillCartella con SKILL.md, caricata a richiestaProcedure ripetibili: scrivere un commit, un ADR, fare triage, review.
SubagenteAgente con prompt e strumenti propri, contesto separatoLavoro specialistico da delegare (es. acme-api per il backend, acme-web per il frontend).
HookComando eseguito su un evento (dopo un edit, prima di un tool)Controlli deterministici: lint, format, blocchi di sicurezza.
Server MCPStrumenti esterni esposti all'agenteAccesso a sistemi: issue tracker, database, browser.
PluginPacchetto installabile di tutto quanto sopraDistribuire e versionare il setup al team.
Regola pratica: se una regola vale sempre, va nelle istruzioni; se è una procedura che serve ogni tanto, è una skill; se deve succedere sempre senza eccezioni, è un hook.

03 Creare una skill

Anatomia: una cartella, un file obbligatorio

.claude/skills/
  new-adr/
    scripts/
---
name: new-adr
description: Crea un nuovo ADR in docs/adr con il numero
  successivo e il template del team. Usala quando si prende
  una decisione architetturale da documentare.
---

# Nuovo ADR

1. Trova il numero con `scripts/next-number.sh`.
2. Parti da [template.md](template.md): il titolo è la decisione,
   il corpo il perché, poi `## Considered Options`.
3. Una decisione cambiata non si riscrive: nuovo ADR e nota
   «Superata da» in cima al vecchio.
4. Il commit dell'ADR è un `docs:` a sé.
# <La decisione in una frase, non l'argomento>

<Che cosa si è deciso e perché, in prosa: vincoli, contesto,
riferimenti agli altri ADR (ADR-0006).>

<Le conseguenze: che cosa diventa più facile e che cosa più difficile.>

## Considered Options

- **<Alternativa>.** Scartato: <motivo>.
- **<Alternativa>.** Rimandato a <fase>: <motivo>.
#!/usr/bin/env bash
# stampa il prossimo numero di ADR a 4 cifre
last=$(ls docs/adr | grep -oE '^[0-9]{4}' | sort | tail -1)
printf '%04d\n' $((10#${last:-0} + 1))

Il frontmatter dice quando usarla, il corpo come. Template e script si leggono o si eseguono solo se il corpo li nomina: lo script non entra nel contesto, ne entra solo l'output.

Il formato è uno standard aperto (Agent Skills, agentskills.io): la stessa cartella funziona in Claude Code, Copilot, Codex, Gemini CLI, Cursor. Cambia solo dove la si mette.
03 Creare una skill

Il frontmatter, campo per campo

CampoA cosa serveDove vale
nameNome del comando /. Minuscole, cifre e trattini, max 64 caratteri.Claude Copilot
descriptionChe cosa fa e quando usarla. È ciò che il modello legge per decidere. Max 1024 caratteri.Claude Copilot
argument-hintSuggerimento nell'autocompletamento, es. "[numero-issue]", tra virgolette.Claude VS Code
disable-model-invocationSolo tu puoi avviarla.Claude VS Code
user-invocablefalse: solo il modello può usarla, sparisce dal menu.Claude VS Code
allowed-toolsStrumenti concessi senza chiedere permesso durante la skill, es. Bash(git diff *).Claude
context: fork + agentEsegue la skill in un subagente con contesto separato.Claude
model, effort, paths, hooksModello, sforzo, file che la attivano, hook propri.Claude

Nel corpo, solo in Claude Code: $ARGUMENTS, $0, $1 per gli argomenti e !`comando` per iniettare l'output di un comando prima che il prompt arrivi al modello.

Per una skill portabile tra i due strumenti basta name + description. I campi extra di Claude Code vengono semplicemente ignorati dove non sono supportati: verificatelo sulla versione di Copilot che usate. argument-hint va tra virgolette: senza, YAML legge le parentesi quadre come una lista.

03 Creare una skill

  
Buone pratiche

  

    
Una skill, un lavoro
Piccole e componibili battono il manuale unico. Se la description contiene «e anche», probabilmente sono due skill.

    
SKILL.md sotto le 500 righe
Il resto va in file di supporto citati dal corpo: il modello li apre solo quando servono.

    
Script per il deterministico
Calcoli, parsing, numerazioni: uno script è più affidabile e costa meno contesto di una spiegazione.

    
Imperativo e verificabile
Passi numerati, criteri di uscita chiari («mostra il messaggio e chiedi conferma prima di committare»).

    
Versionala nel repo
Le skill di progetto passano dalla review come il codice. Chi clona il repo le ha subito.

    
Provala sul serio
Tre richieste realistiche: si attiva quando deve? Resta zitta quando non deve? Il risultato è quello atteso?

  

  
Per chi vuole andare oltre: Claude Code ha anche le eval dei plugin (claude plugin eval) per misurare se una skill si attiva correttamente.

09 Le skill di graphify

  
Il codebase come grafo di conoscenza

  

    

      
graphify è uno strumento open source (safishamsi/graphify) che si installa come skill /graphify per Claude Code, Copilot, Codex, Cursor e Gemini CLI. Trasforma una cartella in un grafo interrogabile.

      
    
        
  • Legge codice, documentazione, schemi SQL, configurazioni e PDF.
    • 
        
  • Il codice è analizzato in locale con tree-sitter, senza LLM.
    • 
        
  • Ogni arco è marcato EXTRACTED (letto nel codice) o INFERRED (dedotto, es. da un documento).
    • 
        
  • Raggruppa i nodi in comunità: le «zone» del sistema.
    • 
        
  • Non è un indice vettoriale: è una mappa di relazioni.
    • 
      

    

    

      
Attenzione al nome

      
Il pacchetto PyPI è graphifyy, con due y. Gli altri pacchetti graphify* non c'entrano.

      
uv tool install graphifyy
# oppure
pipx install graphifyy

    

  

  
Il nome con due y è la prima domanda che arriva sempre: un pacchetto con un nome simile installa tutt'altro.






  
09 Le skill di graphify

  
Che cosa trovi in graphify-out/

  

    
graph.html
Il grafo interattivo da aprire nel browser. Ottimo per l'onboarding su una zona sconosciuta.

    
GRAPH_REPORT.md
Concetti chiave, nodi più collegati, connessioni sorprendenti, domande suggerite. Nelle versioni recenti riporta il commit da cui è stato costruito.

    
graph.json
Il grafo completo: query, path ed explain lo interrogano senza rileggere i sorgenti.

  

  
Buona pratica: metti graphify-out/ in .gitignore, costruiscilo nella checkout principale e scrivi le regole d'uso per gli agenti in un file dedicato, per esempio docs/agents/code-graph.md.

  
Il grafo fotografa i file al momento della costruzione: per questo il report riporta il commit, così si capisce quanto è vecchio.

Far vedere la differenza: senza grafo l'agente fa grep e apre file uno dopo l'altro; con il grafo sa subito quali tre file leggere. Poi però li legge: il grafo dice dove guardare, non che cosa c'è.

  • Costruzione del codice gratuita: tree-sitter in locale, nessun credito LLM.
    • 
      
  • Onboarding: graph.html e le comunità mostrano le zone del sistema.
    • 
    

    
Limiti e buone abitudini
    
      
  • È una mappa: le conclusioni vengono dalla lettura del codice.
    • 
      
  • Invecchia: dopo un pull serve graphify update ..
    • 
      
  • Le query confrontano alla lettera: cerca con i nomi del codice, in inglese.
    • 
      
  • Zero risultati non vuol dire che non esiste: prova altri termini.
    • 
      
  • Per un file che conosci già, aprilo direttamente.
    • 
    

  

  
Sono le regole da scrivere nel file per gli agenti (es. docs/agents/code-graph.md): valgono uguali per le persone.

I comandi

  

    
nell'agente (skill)

/graphify query "come arriva un ordine al pagamento?"
/graphify path "UserService" "DatabasePool"
/graphify explain "RateLimiter"

    
nella shell (senza LLM)

graphify watch                   # aggiorna mentre lavori

graphify path "A" "B" --graph graphify-out/graph.json
graphify explain "OrderService" --graph graphify-out/graph.json

  

  
Flusso del team: il maintainer costruisce il grafo nella checkout principale; gli agenti lo leggono e non lo riscrivono mai da un worktree. In Codex il comando è $graphify.

  
--budget limita i token della risposta. Gli agenti possono usare query, path ed explain dalla shell, con --graph puntato alla checkout principale.

12 Laboratorio · Passo 1

  
Scrivi le tre skill nel repo

  

    

      
      
      
    

    

      
.claude/skills/conventional-commit/SKILL.md
---
name: conventional-commit
description: Scrive il messaggio di commit secondo le convenzioni del team
  (conventional commits, descrizione in italiano, numero dell'issue in fondo).
argument-hint: "[numero-issue]"
disable-model-invocation: true
allowed-tools: Bash(git diff *) Bash(git status *)
---

# Messaggio di commit

1. Leggi le modifiche in stage con `git diff --staged`.
2. Scegli il tipo: feat, fix, refactor, test, docs, chore.
3. Lo scope è l'app o il pacchetto toccato: api, web, mobile, core, types.
4. Descrizione in italiano, senza punto finale, al massimo 72 caratteri.
5. Chiudi con il numero dell'issue: (#$ARGUMENTS).

Esempio: `feat(web): il carrello mostra il totale con la spedizione (#12)`

Mostra il messaggio e chiedi conferma prima di eseguire `git commit`.

    

    

      
.claude/skills/new-adr/SKILL.md
---
name: new-adr
description: Crea un nuovo Architecture Decision Record in docs/adr
  con il numero successivo e il template del team.
argument-hint: "[la decisione]"
disable-model-invocation: true
---

ADR esistenti:
!`ls docs/adr`

Crea `docs/adr/NNNN-<slug>.md`: numero successivo a quattro cifre, slug
in italiano preso dalla decisione. Parti da [template.md](template.md).
Decisione: $ARGUMENTS

- Il titolo è la decisione in una frase, non l'argomento.
- Il corpo spiega in prosa che cosa si è deciso e perché.
- `## Considered Options` elenca le alternative:
  `- **Nome.** Scartato: motivo.` (o Rimandato a …).
- Se la decisione cambia un ADR esistente, non riscriverlo: in cima
  al vecchio aggiungi `> **Superata da ADR-NNNN** su …. Il resto resta in vigore.`

Fammi le domande che mancano sulle alternative, poi scrivi il file.
L'ADR va in un commit `docs:` a sé.

      
.claude/skills/new-adr/template.md
# <La decisione in una frase, non l'argomento>

<Che cosa si è deciso e perché, in prosa: vincoli, contesto,
riferimenti agli altri ADR (ADR-0006).>

<Le conseguenze: che cosa diventa più facile e che cosa più difficile.>

## Considered Options

- **<Alternativa>.** Scartato: <motivo>.
- **<Alternativa>.** Rimandato a <fase>: <motivo>.

      
Il titolo è la decisione stessa: chi scorre docs/adr/ capisce che cosa si è deciso dal solo nome del file. !`ls docs/adr` funziona solo in Claude Code. In Copilot la riga arriva come testo e l'agente esegue il comando da sé: il risultato è lo stesso, con un passaggio in più.

    

    

      
.claude/skills/italian-copy/SKILL.md
---
name: italian-copy
description: >-
  Regole per i testi in italiano del repo: commenti, messaggi
  d'errore, stringhe dell'interfaccia, documentazione. Usala ogni volta che
  scrivi o modifichi testo destinato a persone.
user-invocable: false
---

- Identificatori in inglese, testi in italiano.
- Tono professionale ma non formale; all'utente si dà del tu.
- Un errore dice che cosa è andato storto e come rimediare, senza scuse.
- Usa i termini di CONTEXT.md (carrello, ordine, cliente),
  mai sinonimi inventati.

      
La description contiene :  dopo «del repo», che per YAML separa una chiave dal valore. Nel blocco >- resta testo: senza, claude plugin validate fallisce e Copilot non carica la skill.

    

  

  

    
    
  

  
Metto le skill in .claude/skills perché le leggono sia Claude Code sia Copilot. Chi usa solo Copilot può usare .github/skills.

Impacchetta il plugin e il marketplace

  

    
struttura
team-marketplace/

da lanciare nella cartella che contiene il repo

mkdir -p $M/.claude-plugin $P/.claude-plugin
cp -r acme-shop/.claude/skills $P/skills

cat > $P/.claude-plugin/plugin.json <<'EOF'
{ "name": "team-toolkit", "version": "0.1.0",
  "description": "Commit, ADR e testi in italiano",
  "author": { "name": "Team Acme" } }
EOF

cat > $M/.claude-plugin/marketplace.json <<'EOF'
{ "name": "team-marketplace",
  "owner": { "name": "Team Acme" },
  "plugins": [{ "name": "team-toolkit",
    "source": "./plugins/team-toolkit",
    "description": "Commit, ADR e testi in italiano" }] }
EOF

  

  

    
    
  

  
Il secondo punto è importante: con la skill sia nel repo sia nel plugin, in Copilot vince quella di progetto e la versione del plugin viene ignorata in silenzio.

Claude Code

/skills list

Dopo una modifica al plugin: in Claude Code /reload-plugins; in Copilot le modifiche valgono dalla sessione successiva. Con il marketplace locale e il source relativo, tutti e due leggono i file direttamente dalla cartella, senza copiarli.
