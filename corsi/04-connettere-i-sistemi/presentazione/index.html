01 Perché un connettore

Gli agenti non dovrebbero conoscere gli scanner

Due scanner, due lingue

AppScan dice "Severity": "High", SonarQube "severity": "BLOCKER" e un elenco di impacts. Se l'analyst deve capirle tutte e due, ogni prompt diventa un manuale di API.

Un contratto stabile

Il server MCP espone pochi strumenti con un solo schema di alert. Se domani arriva un terzo scanner, cambia il server, non gli agenti.

Il corso senza permessi

Dietro gli stessi strumenti ci sono due backend: simulato in aula, reale sulla propria macchina. Si sceglie con una variabile, senza toccare prompt e skill (ADR-0004).

02 Lo schema comune

La traduzione, campo per campo

Schema comuneDa AppScanDa SonarQube
severitySeverity: Critical, High, Medium, Low, Informationalimpacts[] con softwareQuality SECURITY; se manca, severity: BLOCKER → critical, CRITICAL → high, MAJOR → medium…
kinddependency se c'è una libreria, altrimenti codecode
locationLocation e Linecomponent senza il prefisso progetto:, e line
cweCwe → CWE-611Non c'è nell'issue: una tabella dalla regola, null se sconosciuta
componentLibreria, versione, versione correttanull
suggestedFixFixRecommendationnull: la correzione sta nella descrizione della regola
detectedAtDateCreatedcreationDate, con il fuso +0000 riscritto

I campi del corso 03 (id, source, rule, severity, title, location, description, suggestedFix) restano con lo stesso nome. Lo schema completo è in mcp/alert.schema.json.

Un campo null è un'informazione: lo scanner non lo dà. Meglio null che un valore inventato dal modello. Il Security Analyst della lezione 05 saprà che per SonarQube la correzione va cercata altrove.

02 Lo schema comune

  
Un id stabile, e che cosa si scarta

  

    
L'id nasce da che cosa segnala

      
Non dall'Id dello scanner, che cambia da una scansione all'altra. Il server prende scanner, regola, file, riga e libreria, ne calcola l'hash e lo accorcia: PAY-160644.

      
    
        
  • Lo stesso problema ha lo stesso id a ogni lettura: la pipeline non lo prende in carico due volte.
    • 
        
  • Due scansioni dello stesso XSS danno un id solo: il secondo è un duplicato.
    • 
        
  • Il formato PAY-160644 è quello che l'hook del corso 03 si aspetta in .pipeline/.
    • 
      

    
La selezione

      

        
ScartatoQuando

        
          
chiusoAppScan Fixed, Noise…; SonarQube risolto o accettato

          
non di sicurezzaSonarQube CODE_SMELL senza impatto SECURITY

          
duplicatoLo stesso id di un alert già preso

          
sotto sogliaMeno grave di min_severity

        
      

      
list_alerts restituisce gli alert e il conto degli scartati per motivo: la tabella dice anche che cosa non mostra.

  

  
Limite da dichiarare: se una modifica al codice sposta l'alert di una riga, l'id cambia. Per il corso va bene; per Heimdall in produzione è una domanda per la lezione 08, quando misuriamo.

03 Il server MCP

  
Il server garantisce il contratto

  

    
mcp/alerts.js · estratto
const alert = { id, project: project.project, ...fields };
// il server garantisce il contratto: un alert fuori schema non esce
const problems = validateAlert(alert);
if (problems.length) {
  throw new Error(`L'alert ${fields.scannerId} di ${project.project}
    non rispetta lo schema comune: …`);
}

    
    
      
  • Ogni alert passa da alert.schema.json prima di uscire. Un normalizzatore sbagliato produce un errore, non un dato strano che l'analyst prende per buono.
    • 
      
  • Un errore torna all'agente come risultato dello strumento, con isError: true: il server non cade e il Data Retriever lo riporta.
    • 
      
  • I messaggi d'errore dicono che cosa manca, mai i valori: «manca la variabile HEIMDALL_SONARQUBE_TOKEN», non il token.
    • 
      
  • alerts-table.js usa lo stesso connettore senza il modello: è la tabella di riferimento.
    • 
    

  

  
Nel laboratorio lo provate: cambiate High in alta nel normalizzatore e guardate l'errore. È la stessa idea della verdict.schema.json del corso 03, spostata alla sorgente.







  
04 Backend e credenziali

  
Due backend, la stessa uscita

  

    
simulated
Gli scenari
Legge scenarios/<progetto>/: project.json e l'export dello scanner. Nessuna rete, nessuna credenziale, sempre lo stesso risultato. È il backend predefinito.

    
real
Le API degli scanner
SonarQube: GET api/issues/search con components. AppScan on Cloud: POST api/v4/Account/ApiKeyLogin, poi GET api/v4/Issues/Application/{id}. Restituisce gli stessi dati grezzi: normalizzazione e selezione sono comuni.

  

  
si sceglie con una variabile
HEIMDALL_BACKEND=real node scripts/alerts-table.js orders-service
# stessi id del backend simulato: cambia da dove arrivano i dati, non che cosa diventano

  
Il backend reale chiama le API REST, non i server MCP ufficiali: lo fissa ADR-0006 e lo motiviamo tra due slide. La chiamata ad AppScan viene dal codice ufficiale di HCL ma non è provata contro il servizio vero: si verifica nella lezione 09.

04 Backend e credenziali

  
E i server MCP ufficiali?

  

    
SistemaServer ufficialeChe cosa sappiamo

    
      
SonarQubeSonarSource/sonarqube-mcp-serverServer e Cloud; SONARQUBE_TOKEN con SONARQUBE_URL o SONARQUBE_ORG; immagine Docker sonarsource/sonarqube-mcp; strumento search_sonar_issues_in_projects

      
AppScanUna pagina della documentazione HCL, per AppScan on Cloud e AppScan 360°Non siamo riusciti a leggerla: configurazione e strumenti non verificati

      
Azure DevOpsmicrosoft/azure-devops-mcpRemoto https://mcp.dev.azure.com/{organization}, in anteprima, o locale con npx -y @azure-devops/mcp {organization}; strumenti per repo, pull request, pipeline e log. Serve nella lezione 07

    
  

  
La scelta (ADR-0006): per gli scanner il backend reale chiama le API REST. Usare i server ufficiali vorrebbe dire un client MCP dentro il nostro server, un processo in più per scanner, Docker per SonarQube, e strumenti di terzi da tradurre a ogni loro rilascio. Gli agenti non li vedono comunque (ADR-0004).

  
Era una domanda aperta del percorso. Per Azure DevOps la stessa scelta si rifà nella lezione 07, quando serve aprire le pull request: lì il server ufficiale copre molto di più di due chiamate.

06 Dove andiamo

  
Heimdall, un pezzo alla volta

  

    

      
Un plugin per Claude Code e Copilot CLI: parte da un alert di sicurezza di AppScan o SonarQube e arriva a una pull request su Azure DevOps, pronta per la review.

      
Data Retriever → Security Analyst → Supervisor → Resolver → CI → Review umana

      
Da oggi: Heimdall esiste. Ha il server MCP con lo schema comune, due backend e il Data Retriever. La lezione 05 gli dà il codice dei progetti e il Security Analyst.

    

    

      
#LezionePezzo di Heimdall

      
      
01Skill e pluginil comando /heimdall, il plugin, il marketplace

      
02Subagenti, hook e server MCPi mattoni: agenti, guard, connettori

      
03Orchestrare più agentila pipeline, il piano rifiutato, i retry

      
04Connettere i sistemi oggiData Retriever e il server MCP degli alert

      
05Capire il codiceSecurity Analyst e piano di remediation

      
06Vincoli e guardrailSupervisor e hook: test intoccabili, niente merge

      
07Dalla patch alla pull requestResolver, conventional commits, CI

      
08Misurare e rendere affidabilei tre scenari come casi di prova

      
09Heimdall in funzione/heimdall remediate sui tre scenari

      
    

  

  
Il piano completo è in docs/percorso-heimdall.md. Heimdall si costruisce da zero nei laboratori di questo repo (ADR-0005), con un ambiente simulato e dati inventati (ADR-0004). Il backend reale chiama le API REST degli scanner (ADR-0006).
